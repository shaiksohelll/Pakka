=== PART 1 — ADR-0037: Realtime fix, codebase-wide audit ===

Symptom (broader than originally documented): Realtime UPDATE/INSERT events do not propagate to already-open opposite tabs. Three confirmed broken sites:
  (a) /worker/feed — when a client posts a new job, it does NOT appear in worker's open feed without refresh.
  (b) /client/jobs/[id] — when a worker applies, the application does NOT appear in client's open detail page without refresh.
  (c) Both milestones pages — milestone status UPDATEs do not propagate either direction (worker submit → client tab; client approve → worker tab).

Migration 202604300002_realtime_replica_identity.sql (REPLICA IDENTITY FULL on milestones / wallets / escrow_ledger) was shipped but did not fix the bug — confirming the root cause is on the client/JS layer, not the Postgres layer. Apply ALL FOUR hypotheses simultaneously and audit EVERY .on('postgres_changes') site in the codebase, not just the milestones pages.

(H2 — setAuth, the most likely root cause) In src/lib/supabase/client.ts:
  - After signInWithOtp / verifyOtp resolves, call `supabase.realtime.setAuth(session.access_token)`.
  - Register an `onAuthStateChange` listener AT MODULE INIT (only once — not inside a hook) that re-calls setAuth whenever a new session arrives.
  - Without this, every channel auths with the anon key, the realtime server evaluates SELECT policies against the wrong JWT, and silently drops the broadcast.

(H3 — filter syntax audit) Grep the entire src/ tree for `.on('postgres_changes'`. Every match must pass `filter` as a STRING (e.g. ``filter: `job_id=eq.${jobId}` ``), never as an object literal. Object-form filters are accepted by TypeScript types but silently no-op at runtime. Report every site you find and confirm fixed.

(H4 — channel cleanup audit) Same grep targets. Every useEffect cleanup that does `channel.unsubscribe()` must be replaced with `supabase.removeChannel(channel)`. Every `.subscribe()` call must be chained with a status callback: `.subscribe((status) => console.log('[<channel-name>]', status))` so DevTools verifies the subscription reaches SUBSCRIBED.

=== PART 3 — ADR-0034: get_application_worker_summary RPC + client-job-detail enrichment swap ===

Symptom: on /client/jobs/[id], application cards render the worker's name as the literal string "Worker" and the trust tier as "Bronze". Root cause: the client session's `.from('profiles').in('id', workerIds)` lookup is RLS-empty (profiles RLS only allows self-read).

Create supabase/migrations/202605020002_application_worker_summary.sql:

  CREATE OR REPLACE FUNCTION public.get_application_worker_summary(
    worker_ids uuid[]
  )
  RETURNS TABLE (
    id uuid, full_name text, trust_tier public.trust_tier,
    rating numeric, jobs_completed integer
  )
  LANGUAGE plpgsql SECURITY DEFINER SET search_path = public
  AS $$
  BEGIN
    RETURN QUERY
    SELECT DISTINCT p.id, p.full_name, wp.trust_tier, wp.rating, wp.jobs_completed
    FROM public.profiles p
    LEFT JOIN public.worker_profiles wp ON wp.profile_id = p.id
    WHERE p.id = ANY(worker_ids)
      AND EXISTS (
        SELECT 1 FROM public.job_applications ja
        JOIN public.jobs j ON j.id = ja.job_id
        WHERE ja.worker_id = p.id
          AND j.client_id = auth.uid()
          AND ja.status <> 'rejected'
      );
  END;
  $$;
  GRANT EXECUTE ON FUNCTION public.get_application_worker_summary(uuid[]) TO authenticated;

Update src/app/client/jobs/[id]/client-job-detail.tsx: replace the two `.in('id', workerIds)` enrichment calls with one `supabase.rpc('get_application_worker_summary', { worker_ids: workerIds })`. Per ADR-0032, check `.error` and throw — never silently default to []. Update src/components/ui/status-badge.tsx (or equivalent) so a null/undefined trust_tier renders an explicit `—` placeholder, not a silent Bronze default.
